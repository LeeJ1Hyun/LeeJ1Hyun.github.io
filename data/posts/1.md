AWS EKS 환경에서 외부 요청을 받을 때 Network Load Balancer(NLB)를 사용한다면 Target Group과 Target Type을 선택해야 합니다.

대부분 Target Group이 무엇인지는 알고 있을 것입니다. 하지만 Target Type에 대해서는 깊게 생각해본 적이 없을 겁니다. 저 또한 문제가 생기기 전까지는 잘 모르고 있었습니다.

## 실제 겪은 문제

실무에서 Istio Service Mesh 환경에서 서로 다른 EKS 클러스터 간 통신 시, Internal NLB를 사용하는데 **간헐적으로 Socket timeout**이 발생하는 문제를 겪었습니다.

**상황:**

- Cluster A의 Pod → Internal NLB → Cluster B의 Istio Ingress Gateway
- Target Type: **Instance**
- 증상: 간헐적으로 Socket timeout 발생, 재시도하면 성공

**해결:**

- Target Type을 **IP**로 변경
- 이후 Socket timeout 완전히 해소

**추측되는 원인: 추가 네트워크 홉(Hop)**

- Instance Type: NLB → Node (NodePort) → kube-proxy → Ingress Gateway Pod (다른 Node일 수 있음)
- IP Type: NLB → Ingress Gateway Pod (직접)
- 클러스터 간 통신에서는 이미 네트워크 레이턴시가 높은데, Instance Type의 추가 홉이 timeout을 유발했을 가능성

이 경험을 통해 알게 된 Target Type의 차이점과 선택 기준을 정리합니다.

## Target Group

Target Group은 **로드 밸런서가 트래픽을 전달할 대상들의 집합**입니다.

쉽게 말해, 여러 서버(EC2 인스턴스, 컨테이너, IP 주소 등)를 하나의 그룹으로 묶어놓은 것입니다. 로드 밸런서는 들어오는 요청을 이 Target Group 내의 대상들에게 분산시킵니다.

**Target Group의 주요 역할:**

1. **트래픽을 받을 대상(Target)들을 관리**

   - Target을 등록/해제하여 트래픽을 받을 서버 목록을 동적으로 관리

2. **각 대상의 Health Check 수행**

   - 설정한 주기마다 각 Target에 Health Check 요청
   - unhealthy 상태의 Target에는 트래픽을 보내지 않음

3. **트래픽 분산 규칙 적용**

   - 로드 밸런싱 알고리즘(Round Robin)에 따라 트래픽을 분산

4. **로드 밸런서와 실제 서버를 연결**

   - Listener가 받은 트래픽을 어떤 Target으로 전달할지 결정하는 중간 다리 역할
   - 포트 매핑을 통해 로드 밸런서 포트와 Target 포트를 다르게 설정할 수 있음
     - ex) NLB는 80번 포트로 요청을 받지만, 실제 애플리케이션은 8080 포트에서 실행

## Target Type

Target Type은 **Target Group이 어떤 방식으로 트래픽을 전달할지 결정하는 타입**입니다.

쉽게 말해, 로드 밸런서가 트래픽을 보낼 때 "EC2 인스턴스 ID"로 찾아갈지, 아니면 "IP 주소"로 직접 찾아갈지를 정하는 것입니다.

아래 다이어그램에서 두 가지 방식의 차이를 확인할 수 있습니다.

### Instance Type

Instance Type은 **EC2 인스턴스 ID**를 직접 타겟으로 지정하는 방식입니다.

위 그림처럼 Instance Type에서는 Load Balancer가 Service를 거쳐 Pod로 트래픽을 전달합니다.

```yaml
# Instance Type 예시
TargetType: instance
Targets:
  - Id: i-1234567890abcdef0
    Port: 80
  - Id: i-0987654321fedcba0
    Port: 80
```

**특징:**

- EC2 인스턴스 ID를 타겟으로 사용
- NodePort를 통한 간접 라우팅 (추가 네트워크 홉 발생)
- Health Check가 NodePort 기반으로 수행

### IP Type

IP Type은 **IP 주소**를 직접 타겟으로 지정하는 방식입니다.

![IP Type 다이어그램](https://private-user-images.githubusercontent.com/100523786/516212050-9050e35e-e62f-4ec9-8587-61911ee5f421.png?jwt=eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.eyJpc3MiOiJnaXRodWIuY29tIiwiYXVkIjoicmF3LmdpdGh1YnVzZXJjb250ZW50LmNvbSIsImtleSI6ImtleTUiLCJleHAiOjE3NjM1NDg3ODUsIm5iZiI6MTc2MzU0ODQ4NSwicGF0aCI6Ii8xMDA1MjM3ODYvNTE2MjEyMDUwLTkwNTBlMzVlLWU2MmYtNGVjOS04NTg3LTYxOTExZWU1ZjQyMS5wbmc_WC1BbXotQWxnb3JpdGhtPUFXUzQtSE1BQy1TSEEyNTYmWC1BbXotQ3JlZGVudGlhbD1BS0lBVkNPRFlMU0E1M1BRSzRaQSUyRjIwMjUxMTE5JTJGdXMtZWFzdC0xJTJGczMlMkZhd3M0X3JlcXVlc3QmWC1BbXotRGF0ZT0yMDI1MTExOVQxMDM0NDVaJlgtQW16LUV4cGlyZXM9MzAwJlgtQW16LVNpZ25hdHVyZT0xZGIzNzJiMzRkMjdkNzMxN2RmNjJlZmJhYTU4MzYzOWI4MjdlNDMyMjZkNzQyZjJhNWQ1Y2E1MDdlMzllMjYwJlgtQW16LVNpZ25lZEhlYWRlcnM9aG9zdCJ9.CL3WgSnTpxmnUKCok5387BLMwUGRB1LDLZ0zJOYuM5s)

위 그림에서 볼 수 있듯이 IP Type에서는 Load Balancer가 각 Pod의 IP로 직접 트래픽을 전달합니다.

IP Type을 사용하는 방식에는 두 가지 패턴이 있습니다:

#### 1안: Service Mesh (Istio) 사용

**아키텍처:**

```shell
Client (203.0.113.45)
  ↓
NLB (IP Type)
  ↓
Istio Ingress Gateway Pod IP (10.0.1.50, 10.0.2.51 등)
  ↓
VirtualService 라우팅
  ↓
실제 애플리케이션 Pod
```

**트래픽 전달 과정:**

1. **Client (203.0.113.45) → NLB**: 클라이언트가 요청 전송
2. **NLB → Ingress Gateway Pod (10.0.1.50) 직접**: Service를 거치지 않고 Gateway Pod IP로 바로 전달
3. **Gateway → 실제 애플리케이션 Pod**: VirtualService 라우팅 규칙에 따라 전달

**특징:**

- NLB → Ingress Gateway Pod IP로 직접 전달
- Gateway에서 Client IP 보존
- 중앙화된 트래픽 관리 (라우팅, 모니터링)

#### 2안: Service Mesh 없이 직접 연결

**아키텍처:**

```shell
Client (203.0.113.45)
  ↓
NLB (IP Type)
  ↓
애플리케이션 Pod IP (10.0.1.10, 10.0.2.20 등)
```

**트래픽 전달 과정:**

1. **Client (203.0.113.45) → NLB**: 클라이언트가 요청 전송
2. **NLB → Pod (10.0.1.10) 직접**: Service를 거치지 않고 Pod IP로 바로 전달
3. **Pod가 받는 요청**: Source IP = `203.0.113.45` (실제 클라이언트 IP)

**특징:**

- 가장 직접적인 연결 방식
- Service Layer를 우회하여 SNAT 없음
- 단순한 구조로 관리 용이

```yaml
# Target Group 예시
TargetType: ip
Targets:
  - Id: 10.0.1.10
    Port: 80
  - Id: 10.0.2.20
    Port: 80
```

**공통 특징:**

- IP 주소를 직접 지정
- 컨테이너, 람다, 온프레미스 서버 지원

## 주요 차이점

위 두 다이어그램을 비교해보면 가장 큰 차이점을 확인할 수 있습니다:

**주요 차이점 비교:**

| 구분                     | Instance Type          | IP Type                              |
| :----------------------- | :--------------------- | :----------------------------------- |
| **NLB의 Client IP 보존** | 활성화 (기본값)        | 비활성화 (TCP/TLS 기본값, 설정 가능) |
| **타겟 범위**            | EC2만                  | EC2, ECS, Lambda, 온프레미스         |
| **Pod IP 변경**          | 영향 없음              | 자동 재등록 (LB Controller가 처리)   |
| **추가 Network Hop**     | 있음 (kube-proxy 경유) | 없음 (Pod 직접 전달)                 |

> **참고: EKS에서의 자동 관리**
>
> 일반 Kubernetes 환경에서는 Pod IP가 변경되면 수동으로 Target Group을 업데이트해야 합니다. 하지만 **EKS 환경**에서는 두 가지 컴포넌트가 자동으로 처리합니다:
>
> 1. **AWS VPC CNI**: Pod에 VPC의 실제 IP 주소를 할당 (ENI 기반)
> 2. **AWS Load Balancer Controller**: Kubernetes Service를 감시하여 Pod 생성/삭제/IP 변경 시 Target Group을 자동으로 업데이트
>
> 이 두 컴포넌트 덕분에 EKS에서는 Pod가 재시작되거나 스케일링되어도 관리자의 수동 개입 없이 트래픽이 올바른 Pod로 라우팅됩니다.

## 선택 기준

### Instance Type을 선택하는 경우:

1. **전통적인 EC2 기반 워크로드**

   - Kubernetes를 사용하지 않는 일반 EC2 환경
   - NodePort를 사용하는 레거시 구조

2. **간단한 설정**으로 빠르게 시작하고 싶은 경우
   - 기본 설정만으로 동작
   - Auto Scaling Group과의 연동이 쉬움

> **제약사항**: EKS 환경에서는 추가 네트워크 홉으로 인한 지연과 Client IP 손실 문제가 있을 수 있습니다.

### IP Type을 선택하는 경우:

1. **EKS 컨테이너 환경**

   - Pod로 직접 라우팅하여 네트워크 효율성 극대화
   - AWS Load Balancer Controller가 Pod IP를 자동 관리

2. **성능이 중요한 마이크로서비스**
   - 낮은 레이턴시가 필요한 경우
   - 높은 처리량(throughput)이 요구되는 경우

> **참고**: [AWS 공식 문서](https://docs.aws.amazon.com/ko_kr/elasticloadbalancing/latest/network/load-balancer-target-groups.html)에 따르면, EKS 환경에서는 대부분의 경우 IP Type이 권장됩니다.

## 결론

EKS 환경에서 NLB Target Type 선택의 핵심은 **워크로드 특성과 네트워크 효율성**입니다.

**Instance Type:**

- EC2 기반 전통적인 워크로드에 적합
- EKS 환경에서는 NodePort를 통한 간접 라우팅으로 추가 홉 발생
- 클러스터 간 통신이나 고성능 요구사항에는 부적합

**IP Type:**

- EKS 컨테이너 환경에 최적화
- Pod로 직접 라우팅하여 네트워크 효율성 극대화

실무 경험상, Istio Service Mesh 환경에서 **Instance Type → IP Type 변경만으로도 Socket timeout 문제가 해결**되었습니다.
